# Notemap: временные ссылки с фотографиями

Согласовано 18.10.2026: облачные ссылки на полную коллекцию с фото, Supabase Free, срок 7 дней. Личные заметки остаются в IndexedDB; в облако попадает только выбранный неизменяемый снимок. Новая ссылка → diff → ручное подтверждение. Никакой фоновой синхронизации. Cron используется исключительно для удаления просроченных публикаций.

## Настройка бесплатного проекта

1. SQL Editor: выполнить `migrations/202610180001_share_snapshots.sql`. Создаётся закрытый bucket `notemap-shares`, таблица с RLS без клиентских политик и серверная атомарная квота.
2. Authentication → Sign In / Providers → Anonymous: включить anonymous sign-ins. Сессия создаётся только при явном нажатии «Создать ссылку», отдельная регистрация пользователю Notemap не нужна. Применяются ограничения Auth по IP; для открытого массового запуска потребуется оценить CAPTCHA.
3. Edge Functions: создать `share-snapshot`. Исходники — `functions/share-snapshot/`. Для редактора Dashboard можно объединить `handler.ts` и `index.ts`, убрав строку импорта. `verify_jwt=false`, поскольку публичное чтение использует случайный токен, публикация сама проверяет JWT через Auth, очистка проверяет отдельный случайный токен из Vault через закрытый серверный RPC. Встроенные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` остаются только на сервере.
4. Функции задать `NOTEMAP_ORIGINS`: разрешённые origin через запятую. Например `https://sumergeg.github.io,http://localhost:5175,http://localhost:5173`. Отклоняются другие browser origin; CORS сам по себе не заменяет авторизацию.
5. Dashboard → Vault: сохранить `notemap_project_url`. Затем SQL Editor: выполнить `cleanup-schedule.sql`: он генерирует отдельный токен очистки внутри Vault и закрытый RPC его проверки. Service-role key не копируется в Vault, исходники, VITE_, Actions variables или чат.
6. В `apps/web/.env.local` и публичных GitHub Actions variables нужны только `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.

## Срок и удаление

Срок вычисляет БД при публикации: ровно 7 дней. Чтение через Edge Function сразу блокируется после `expires_at`, независимо от того, успела ли выполниться очистка. Bucket закрытый, долгоживущих публичных URL на фото нет, клиентские ответы `no-store`. Токен 256 бит находится во fragment ссылки, в базе хранится SHA-256; он не передаётся в URL API и не записывается приложением в логи.

Ежечасно, в 7 минут каждого часа, Cron вызывает функцию с действием `cleanup`. Она удаляет до 100 просроченных архивов за запуск, а также незавершённые загрузки старше часа. Сначала Storage API удаляет реальные байты, только потом удаляется строка БД. При ошибке запись сохраняется для следующего запуска. Нельзя заменять это на SQL DELETE из `storage.objects`: такая команда не удаляет файл.

Обычно байты удаляются при следующем ежечасном запуске; очередь, ошибка сервиса или пауза Supabase Free могут задержать физическое удаление. Поэтому это не гарантия удаления из всех копий/резервов провайдера в конкретную минуту. Импортированные копии и фото на устройствах получателей очистка не затрагивает.

## Ограничения

Один JSON-архив содержит сведения и все выбранные фото в base64: до 40 МиБ после кодирования (примерно до 30 МиБ фото), до 1000 мест, до 10 фото у места. Более крупные коллекции не обрезаются: публикация останавливается с понятной ошибкой. Фотографии проверяются, декодируются и очищаются от EXIF перед публикацией и при получении. Локальные фото владельца не изменяются.

Квота приложения: до 5 хранимых публикаций на облачную анонимную сессию, общий резерв до 800 МиБ; резервирование сериализовано транзакционной блокировкой. До завершения загрузки ссылка не читается. Квота не обходится параллельными загрузками, но не является полной защитой от злонамеренной массовой регистрации. За исходящий трафик отвечает лимит Supabase Free. Платный тариф не включать автоматически.

Смена устройства/очистка браузера не переносит анонимную облачную сессию. Это не аккаунт синхронизации. Ссылки хранятся в локальной истории, а независимые копии с фото входят в резервную копию устройства. Персональные файлы обмена без фото продолжают работать без Supabase.

## Контроль перед публикацией

- Реальная загрузка коллекции с фото, открытие ссылки в другом браузере/профиле, импорт и отключение сети после импорта.
- Новая версия по новой ссылке: diff фотографий, подтверждение, личные заметки не меняются.
- Истёкший тестовый снимок: HTTP 410, затем реальное удаление байтов, сохранение локального импорта.
- Нет прямого чтения bucket / таблицы с publishable key, невозможно вызвать cleanup с браузерным ключом.
- Cron в `cron.job`, результат в `cron.job_run_details` и `net._http_response`; не выводить заголовки авторизации или содержимое коллекции.

Локальные unit-тесты не заменяют эту проверку проекта Supabase. Если проект ещё не настроен, не утверждать, что облачный обмен уже работает.

Официальные инструкции: https://supabase.com/docs/guides/functions/schedule-functions и https://supabase.com/docs/guides/storage/management/delete-objects.
